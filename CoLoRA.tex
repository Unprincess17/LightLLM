\begin{abstract}
Large-scale LLM serving is increasingly shaped by the convergence of sparse Mixture-of-Experts (MoE) base models and LoRA-based multi-tenant adaptation. In multi-LoRA MoE serving, tenant-specific LoRA modules are attached to sparsely activated expert layers, creating a regime where the effective unit of caching is a joint expert--LoRA object. Our trace-driven analysis shows this shift weakens hot-set concentration, reducing cache hit rates by up to 56\% compared to LoRA serving in dense models, and pushing performance degradation into the tail latency.

We present CoLoRA, a serving runtime that treats GPU memory misses as an execution-first recovery problem rather than a promotion-first caching problem. CoLoRA adopts a residency-aware hot/cold dual-path design: GPU-resident objects execute on the hot path, while GPU-cold objects trigger a CPU cold path that computes only the LoRA residual from host-resident weights and merges it back for the current token. CoLoRA further incorporates deferred promotion and temporal prefetching to improve future reuse and partially overlap cold-path latency. By decoupling cold-object execution from GPU residency management, CoLoRA prevents pipeline stalls during cache misses while preserving GPU compute saturation for hot tenants. Under high memory pressure, CoLoRA reduces P99 and P50 Time-Per-Output-Tokens (TPOT) latencies by XX\% and XX\%, respectively, over state-of-the-art baselines such as S-LoRA, while maintaining comparable throughput.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Large-scale LLM serving is increasingly shaped by the convergence of two trends: sparse Mixture-of-Experts (MoE) base models~\cite{todo:moe-llm} and LoRA-based multi-tenant adaptation~\cite{hu2022lora,todo:lora-serving}. In practice, these trends meet in \emph{multi-LoRA MoE serving}. While existing multi-LoRA systems target dense modules such as attention layers and shared FFNs, they do not directly address adaptation on sparsely activated MoE expert layers~\cite{hu2022lora,todo:lora-serving}. This gap is critical: MoE expert FFN blocks comprise the majority of model capacity, making them the natural target for tenant-specific specialization~\cite{todo:moe-knowledge-capacity, schulman2025lora}. This combination couples the compute efficiency of MoE with the parameter efficiency of LoRA. However, it creates a new serving regime in which request-time sparse routing and tenant-specific adapter selection jointly shape the active weights. This significantly enlarges and diversifies the inference working set, rendering it difficult to manage with existing caching strategies.

While LoRA is widely used as a lightweight mechanism for tenant-specific customization, existing multi-LoRA serving systems have largely been designed for dense-model adaptation rather than expert-layer adaptation in sparse MoE models~\cite{hu2022lora,todo:lora-serving}. Extending LoRA to MoE expert layers is both natural and practically important, because expert FFN blocks account for a large fraction of model capacity and provide a high-leverage target for task- or tenant-specific specialization~\cite{todo:moe-knowledge-capacity, schulman2025lora}. This combination is appealing from a deployment perspective: MoE reduces base-model compute, while LoRA enables efficient per-tenant customization without replicating the full model. However, it also creates a distinct serving regime in which dynamic sparse routing~\cite{todo:moe-routing-dynamics} and long-tailed multi-tenant adaptation~\cite{todo:slora} jointly determine which expert- and adapter-side weights are needed for each request, increasing access diversity and complicating locality management during inference.

This enlarged and more diverse working set becomes especially problematic during \emph{decode} in prefill--decode deployments~\cite{todo:pd-serving}. Unlike prefill, which can often amortize weight-loading costs across many prompt tokens, decode operates under tight inter-token latency SLOs: generation is highly memory-bandwidth bound, and any weight miss on the critical path directly translates to pipeline stalls and ITL degradation. Consequently, the granularity of weight management becomes critical: in pure MoE serving, the natural unit is the expert; in conventional multi-LoRA serving, it is the adapter, and prior systems such as S-LoRA~\cite{sheng2024slora} and VaLoRA~\cite{mi2025empower} therefore adopt adapter-centric designs that assume dense adapter loading. In multi-LoRA MoE decode, however, a request only needs the LoRA residuals for the selected experts, so the effective unit of access and reuse is neither an expert alone nor an adapter alone, but a joint expert--LoRA object. These objects are substantially larger than the attention-side LoRA units emphasized in prior systems, because expert-layer LoRA scales with the FFN intermediate dimension (typically 4$\times$--8$\times$ the model width), whereas attention-side LoRA targets the narrower head projections~\cite{todo:moe-ffn-architecture}. At the same time, the base MoE model typically already occupies most device memory, leaving only limited residual VRAM for caching such objects~\cite{zhu2024deepseek}. This breaks the locality assumptions of prior caches: the enlarged and fragmented working set prevents concentration of hot expert--lora pairs, leading to cache thrashing and unpredictable decode latency.

To quantify the locality regime introduced by multi-LoRA MoE decode, we conduct a trace-driven study using Alibaba LoRA serving traces augmented with realistic MoE expert routing patterns~\cite{lin2025understanding}. The study shows that once access is modeled at the granularity of joint expert--LoRA objects, the hot set becomes markedly less concentrated. As shown in Figure~\ref{fig:motivation-breakdown}(a), access locality is highly concentrated under expert-only granularity: the top 2K cached objects cover 98.4\% of accesses. Under realistic joint-object modeling, however, this concentration collapses—the same top-2K set covers only 13.9\% and 21.8\% of accesses under independent (C1) and correlated (C2) adapter--expert assignment, respectively. This fragmentation makes simply adding cache capacity far less effective. In Figure~\ref{fig:motivation-breakdown}(b), the expert-only oracle reaches its target P99 TPOT with a cache that stores just 2K objects, whereas the realistic joint-object workloads still fail to reach that same target even when the cache is expanded to 65K objects (over 32$\times$ larger). At the cache budget where expert-only modeling has already reached diminishing returns, the penalty concentrates in the extreme tail: median TPOT remains near 1.2,ms, but P99 TPOT rises to 6.70,ms, a 5.6$\times$ slowdown (Figure~\ref{fig:motivation-breakdown}(c)). Together, these results show that in multi-LoRA MoE decode, capacity misses are not transient anomalies that can be eliminated by modest cache growth; they are persistent tail events on the decode critical path.

Once GPU capacity misses become unavoidable, the central problem shifts from \emph{how to avoid misses} to \emph{how to serve them on the decode critical path}. Existing GPU-centric systems typically handle a miss with a load-then-run policy: the required weights are first promoted from host memory to GPU memory, and execution resumes only after that promotion completes~\cite{todo:gpu-offload}. This approach is effective when misses are infrequent and future reuse is sufficient to amortize migration cost. In multi-LoRA MoE decode, however, a capacity miss often incurs PCIe transfer latency that dwarfs the lightweight LoRA kernel executing for a single token, leaving minimal compute work to amortize transfer latency or guarantee near-term reuse. In this regime, promotion-first recovery fails not merely due to PCIe bandwidth limits, but because weight transfer becomes a blocking synchronization point that directly stalls the token generation pipeline. The resulting systems question is therefore: when a joint expert--LoRA object is GPU-cold, should the current token stall for synchronous promotion, or should the miss take a different execution path?

We design CoLoRA, a decode-time runtime for multi-LoRA MoE serving that replaces blocking promotion-first recovery with execution-first heterogeneous miss recovery. CoLoRA uses a residency-aware hot/cold dual-path design for expert--LoRA computation during decode. Cache-resident adapters remain on the GPU hot path, while GPU-cold adapters are handled through a separate cold path rather than triggering immediate synchronous promotion. Crucially, CoLoRA does not offload the full expert computation to the CPU, nor does it assume host execution is generally faster than GPU execution. Instead, it exploits a decode-time data-movement asymmetry: computing a cold LoRA residual on the CPU exchanges only per-token activation vectors, whereas promotion-first recovery must first transfer the full expert--LoRA weight object to the GPU. The base MoE expert computation therefore remains on the GPU, while the corresponding cold LoRA residual is computed on the CPU from host-resident weights and merged back for the current token. By detaching only the cold LoRA contribution from blocking promotion, CoLoRA treats GPU-cold misses as bounded heterogeneous execution events rather than unconditional migration barriers on the decode critical path.

\section{Background, Motivation, and Challenges}
\label{sec:background}

\subsection{Background: Expert-LoRA Computation}
\label{subsec:background}

In multi-LoRA MoE serving, decode-time execution combines two forms of request-dependent variation. For each generated token, the shared MoE base model dynamically routes computation to a small subset of experts, while each request also carries its own tenant-specific or task-specific LoRA adaptation. As a result, decode repeatedly depends on both routed expert weights and the corresponding LoRA states for the active request, creating a fine-grained and highly variable parameter access pattern on the per-token critical path.

This access pattern changes the natural unit at which the system should reason about locality and misses. In dense multi-LoRA serving, adapter-level reasoning is often sufficient because accesses tend to concentrate on one adapter's weights. In MoE decode, however, LoRA computation is needed only for the experts selected for the current token. The relevant access unit is therefore neither an expert alone nor an adapter alone, but their joint use in decode, which we call an \emph{expert--LoRA joint object}.

This distinction is especially important during decode. Unlike prefill, decode operates with persistently small effective batch sizes, repeats routing and weight-access decisions once per token, and exposes miss-handling overheads directly in token latency. As a result, when expert--LoRA joint objects cannot be kept within practical GPU cache budgets, the systems challenge is not only how to manage GPU residency, but also how to recover GPU-cold misses without inflating per-token latency.

\subsection{Motivation: Joint-Object Modeling Fragments Decode Locality}
\label{subsec:motivation}

%\subsubsection{Expert--LoRA Joint Objects as the Relevant Access Unit}
%\label{subsec:joint-object}
\noindent {\bf Expert--LoRA Joint Objects Are the Relevant Decode Access Unit.}
A central question is what abstraction the system should use to reason about locality, residency, and misses.

In sparse MoE decode, each token activates only a small subset of experts. When multiple LoRA adapters coexist, accesses no longer concentrate on entire adapters or on experts alone, but on the LoRA states associated with the routed experts for the current request. The effective unit of access and reuse is therefore neither an expert alone nor an adapter alone, but their combination, which we refer to as an \emph{expert--LoRA joint object}.

Reasoning at coarser granularity obscures this access pattern. Adapter-level management is too coarse because it groups many expert slices together with the few actually needed for the current token. Expert-level management is incomplete in multi-tenant serving because it ignores adapter identity: although the routed expert set may repeat across requests, the associated LoRA adapters vary across tenants, so collapsing accesses by expert alone systematically overestimates reuse. To understand the systems consequences of this shift in access granularity, we next compare decode locality and runtime behavior under expert-only and expert--LoRA joint-object views.

\subsubsection{Joint Objects Fragment Decode Locality}
\label{subsec:case-study}

To examine whether this finer-grained access view matters in practice, we conduct a trace-driven case study under three workload conditions.
\texttt{C0} uses expert-only keys.
\texttt{C1} uses expert--LoRA joint keys under independent assignment, where adapter identity is sampled independently of expert routing.
\texttt{C2} uses the same expert--LoRA joint keys under correlated assignment, where certain adapters are more likely to co-occur with specific experts.
This setup separates the effect of finer-grained keying itself from the extent to which structured adapter--expert affinity can partially preserve locality.
We use Alibaba trace~\cite{lin2025understanding} to model LoRA serving request arrivals and LoRA invocations, and replay the resulting decode access streams under these conditions.

As illustrated in Figure \ref{fig:motivation-breakdown}, modeling accesses as joint objects triggers a cascade of system-level degradations, demonstrating that traditional caching strategies are insufficient for this workload.

\paragraph{Locality breaks under joint objects.}
Moving from coarse-grained to joint-object modeling severely fragments decode locality. Figure \ref{fig:motivation-breakdown}(a) shows that the access distribution flattens substantially when expert routing and adapter identity are modeled jointly. Because the access frequency is distributed across a combinatorial space of expert--lora pairs, the "hot set" shrinks in dominance. Consequently, a bounded GPU cache captures a significantly smaller fraction of total accesses, leading to longer reuse distances and frequent cold starts.

\paragraph{Cache scaling loses effectiveness.}
Because locality is fundamentally weakened, simply increasing GPU cache capacity does not resolve the problem. Figure~\ref{fig:motivation-breakdown}(b) shows that, although the expert-only layout reaches its target P99 TPOT with only 2K cached objects, the joint-object layouts remain substantially above the same target across the entire cache sweep and still fail to recover it even at 65K cached objects. This means the issue is not merely insufficient cache capacity: once object granularity destroys locality, scaling cache size yields limited benefit. In practice, systems must therefore operate under constrained budgets where cold misses remain unavoidable.

\paragraph{Tail latency explodes under misses.}
The most severe consequence of this locality fragmentation manifests in request latency. Figure \ref{fig:motivation-breakdown}(c) evaluates Time Per Output Token (TPOT) under a practical GPU cache budget. While the median TPOT remains near-optimal at approximately 1.2 ms, the degradation is heavily concentrated in the tail. P99 latency increases by roughly 5.6x. Because decode operations repeat routing and parameter-access decisions token by token, cold misses stall the synchronous execution path, disproportionately penalizing tail requests that happen to traverse un-cached expert--LoRA intersections.

Taken together, these results sharpen the systems bottleneck in multi-LoRA MoE decode. Once expert--LoRA joint objects become the effective unit of access, the issue is no longer only whether the cache is efficient in the traditional sense, but whether inevitable cold misses can be serviced without directly inflating token latency. This naturally shifts attention from locality alone to the feasibility of alternative miss-handling strategies on the decode critical path.

\subsubsection{Feasibility of Execution-First Recovery on Decode}
\label{subsec:feasibility}
The results above show that, under practical GPU cache budgets, cold misses remain persistent once expert--LoRA joint objects become the effective unit of access. The next question is therefore not just how to expand the hot set, but whether miss handling itself can be restructured to better match decode-time constraints. Decode is a particularly favorable setting for this question: execution advances token by token, per-adapter batches are small, and misses across requests are often only partially synchronized. These properties create opportunities for overlap, making it plausible to treat miss recovery as an execution problem rather than solely as a residency problem.

\begin{figure}[t]
  \centering
  \includegraphics[width=\linewidth]{figures/miss_cost_compare.pdf}
  \caption{
    \textbf{Promotion-first vs. execution-first synchronous miss cost.}
    Promotion-first recovery restores the full expert--LoRA object before execution can resume, making weight migration part of the current token's foreground miss cost.
    Execution-first recovery instead exchanges activation/residual-sized state, computes only the missing LoRA contribution on the CPU, and merges the result back into the decode stream.
    The key distinction is therefore what data must be moved synchronously on the decode critical path, rather than a claim that CPU execution is universally faster.
  }
  \label{fig:miss-cost-compare}
\end{figure}

A key observation is that a decode-time cold miss introduces an asymmetry between restoring residency and serving the current token, as shown in Figure~\ref{fig:miss-cost-compare}. 
Under a conventional promotion-first policy, the system must first move the missing expert--LoRA object into GPU memory and only then resume execution. However, for the current token, what is immediately needed is not full residency restoration as a goal in itself, but completion of the missing expert--LoRA contribution for the routed expert. This distinction matters because expert-layer LoRA objects are relatively large, whereas the per-token activation state involved in the current decode step is comparatively small. As a result, the synchronous cost of promotion-first recovery is dominated by moving a large weight object onto the device before useful work can continue.

This asymmetry suggests that feasibility should be judged not by asking whether CPU execution is universally faster than GPU execution, but by asking what portion of miss-recovery latency must appear on the current token's critical path. If the system can complete the missing LoRA contribution by exchanging activation-sized state while leaving the base expert computation on the GPU, then a cold miss no longer has to be treated as an unconditional residency-restoration barrier. Instead, it can be handled as a bounded execution event whose visible cost depends on how much of that work can be overlapped with other ready GPU computation.

This perspective is especially relevant in multi-tenant MoE decode, where mixed hit/miss batches are common and misses are not perfectly synchronized across requests. In such settings, forcing every cold object through immediate promotion risks turning a per-request miss into a group-wide stall. By contrast, an execution-first design has the potential to isolate the miss to the faulting request while allowing other ready requests to continue making progress on the GPU. The goal, therefore, is not to replace GPU execution for the common case, but to provide a miss-recovery path whose exposed latency is better matched to the decode-time cost structure of joint expert--LoRA accesses.

This argument does not imply that execution-first recovery is always preferable. When adapter diversity is low, the effective working set fits comfortably in GPU memory, or near-term reuse is strong enough to amortize immediate promotion, a load-then-run policy becomes more competitive. CoLoRA therefore targets the regime identified by Figure~\ref{fig:motivation-breakdown}: cache-pressured multi-LoRA MoE decode, where joint-object locality is structurally fragmented, cold misses remain unavoidable, and miss recovery should be optimized for exposed latency rather than immediate residency restoration.


\subsection{Challenges}
\label{subsec:challenges}

The empirical results above reveal a fundamental shift in the role of caching for multi-LoRA MoE decode serving. Once expert--LoRA joint objects become the effective unit of access, locality degradation makes cold misses difficult to eliminate within practical GPU cache capacity alone. Cold misses are therefore no longer rare anomalies that can be absorbed by a sufficiently large hot set. Instead, they become persistent events on the latency-critical decode path, and the dominant systems question shifts from how to avoid every miss to how to recover unavoidable misses without inflating per-token latency.

Realizing this shift in a practical serving runtime requires addressing three challenges.

\paragraph{Challenge 1: Reasoning at expert--LoRA granularity under expanded and fragmented working sets.}
\label{subsec:challenge-residency}

Under joint-object modeling, the effective key space expands substantially, while reuse becomes weaker and more fragmented across requests. This makes coarse-grained management ineffective: adapter-level residency retains many expert slices that are never touched, whereas expert-only reasoning overestimates reuse by ignoring adapter diversity. At the same time, naive fine-grained residency increases fragmentation pressure on the effective hot set and makes limited GPU capacity more vulnerable to transient cold objects.

The system must therefore reason at expert--LoRA granularity, which matches actual computation, without assuming that caching alone can absorb the resulting working-set expansion.

\paragraph{Challenge 2: Recovering cold misses without forcing promotion-first stalls on decode.}
\label{subsec:challenge-miss}

In this regime, many misses correspond to cold objects whose near-term reuse is too limited to amortize immediate promotion. If the system continues to apply a conventional load-then-run policy, each such miss becomes a blocking recovery event: the current token must wait for weight migration before expert--LoRA computation can proceed. Under decode-time latency sensitivity, this directly amplifies tail latency.

The system therefore needs a different default recovery strategy for cold misses. Instead of forcing all misses through immediate GPU promotion, it must provide a way to complete the current expert--LoRA computation without making promotion the only recovery path, while still preserving the option to promote objects later when future reuse justifies it.

\paragraph{Challenge 3: Making cold-path recovery practical under decode constraints.}
\label{subsec:challenge-overlap}

Changing the miss-recovery abstraction is not sufficient by itself. If cold-path execution is too slow, the system merely replaces GPU promotion stall with CPU-side stall. If it is poorly integrated with the decode pipeline, heterogeneous execution introduces a new source of queueing and tail behavior rather than alleviating the original one.

The system must therefore make cold-path recovery efficient enough to operate at small, irregular decode batch sizes, and organize execution to preserve opportunities for overlap between cold-miss handling and GPU hot-path or base-model computation whenever dependencies allow. The challenge is not only to provide an alternative recovery path, but to ensure that this path reduces exposed miss latency instead of becoming a new bottleneck.

\section{Design}
\label{sec:design}

CoLoRA is designed for the regime identified in Section~\ref{subsec:challenges}: once the effective unit of access becomes the expert--LoRA joint object, cold misses remain persistent under realistic GPU memory budgets and cannot be treated as rare exceptions. The central systems goal therefore shifts from eliminating every miss to ensuring that an unavoidable miss does not become a synchronization point on the latency-critical decode path.

More concretely, CoLoRA addresses the three challenges above through three coordinated commitments. First, it adopts the expert--LoRA joint object as the fundamental unit of residency, admission, and miss handling, matching the true granularity of routed computation. Second, it replaces promotion-first miss recovery with an execution-first policy that completes the current access without requiring immediate GPU restoration. Third, it makes this policy practical for decode by providing a bounded, overlap-oriented cold path, a decoupled scheduler, and locality-driven background mechanisms that improve future accesses without reintroducing blocking recovery.

\paragraph{Expert--LoRA object as the control unit.}
This design begins by making the expert--LoRA joint object the uniform unit of control throughout the runtime. Residency checks, admission decisions, miss handling, and background optimization are all expressed at this granularity. This choice directly addresses Challenge~1: adapter-level reasoning retains many expert slices that are never touched, while expert-only reasoning overestimates reuse by ignoring adapter diversity. By operating at expert--LoRA granularity, CoLoRA matches the actual computation induced by routing. At the same time, it does not assume that fine-grained management alone restores locality. Instead, it treats the enlarged and fragmented working set as the operating regime, and builds recovery and optimization mechanisms around that regime.

\subsection{Hot/Cold Execution-First Architecture}
\label{subsec:dual-path-handling}

\begin{figure}[h]
  \centering
  \includegraphics[width=\linewidth]{figures/architecture.pdf}
  \caption{\textbf{CoLoRA's execution-first hot/cold architecture for decode-time expert--LoRA serving.} Routed expert--LoRA accesses first check GPU residency. Hits stay on the GPU hot path. Misses are peeled off to a CPU cold path that computes the missing contribution using host-resident parameters and later reinserts the result. Promotion is deferred and decoupled from foreground miss recovery, serving only future reuse.}
  \label{fig:CoLoRA_overview}
\end{figure}

This component addresses Challenge~\ref{subsec:challenge-miss} directly and establishes the basis for Challenge~\ref{subsec:challenge-overlap}. Since cold expert--LoRA objects often do not exhibit enough near-term reuse to justify immediate promotion, CoLoRA changes the default action on a miss. Rather than synchronously restoring the missing object to GPU memory and only then resuming execution, it prioritizes completing the current computation using whatever resources are immediately available.

\paragraph{Execution-first principle.}
The key principle is therefore execution first, promotion later. For the current token, progress should be guaranteed by the fastest available execution path, not by mandatory restoration of residency. Promotion remains useful, but only as an optimization for future accesses. This separation is central to the design: the mechanism that guarantees forward progress for the current request is decoupled from the mechanisms that improve locality for future requests.

\paragraph{Hot/cold dual path.}
CoLoRA realizes this principle through a hot/cold dual-path architecture for decode-time expert--LoRA execution. When the required expert--LoRA object is resident in GPU memory, execution proceeds entirely on the GPU hot path, preserving the normal fast path. When the object is absent, the request is diverted to a CPU cold path that computes the missing expert--LoRA contribution using host-resident parameters. The miss therefore no longer forces the entire execution group to wait for immediate promotion.

\paragraph{Skip-and-reinsert execution.}
The runtime implements this behavior through a skip-and-reinsert discipline. Suppose request $i$ encounters a miss at layer $L$. Rather than blocking the entire GPU execution group, the scheduler temporarily removes request $i$ from the current group, stages the necessary activation state for host-side execution, and allows the GPU to continue processing other ready requests at the same layer. Once the CPU cold path finishes the missing computation, the result is returned to device memory and request $i$ resumes from its next execution point. In effect, a cold miss delays only the request that incurs it, rather than serializing all requests that happen to be co-scheduled with it.

\paragraph{Correctness invariants.}
This execution model preserves three invariants that are critical to correctness. First, each request still advances strictly in layer order. Second, different requests may become temporarily out of phase, which creates room for overlap rather than forcing lockstep progression. Third, a miss in one request does not block the progress of other ready requests. Together, these invariants convert unavoidable cold misses from group-wide stalls into localized delay.

This design is particularly well suited to decode-time serving, where per-adapter batches are small, routing varies across requests, and cold misses are only partially aligned in time. Under these conditions, the GPU hot path often continues to have useful work even when some requests are diverted to the cold path. The key question is therefore not simply how expensive cold-path execution is in isolation, but how much of that cost can be hidden off the critical path. We next characterize that cost and contrast it with promotion-first handling.

\subsubsection{Cost Structure of Cold-Path Execution}
\label{subsec:analytical-formulation}

\paragraph{Latency decomposition.}
To formalize the feasibility argument above, we model execution-first recovery in terms of the latency components that can become visible on the current token's decode path. The relevant question is not whether host execution is universally faster than GPU execution in isolation, but whether miss handling can be converted from a weight-restoration bottleneck into a bounded side path whose exposed latency can be reduced through overlap.

Under execution-first handling, a cold miss is served by exporting the token's activation state to the host, computing only the missing LoRA contribution there, and returning the result to the device for reintegration. The service time of such a cold-path invocation can be decomposed as
\begin{equation}
T_{\text{cold}} = T_{\text{pack}} + T_{\text{D2H}} + T_{\text{cpu}} + T_{\text{H2D}} + T_{\text{merge}},
\end{equation}
where $T_{\text{pack}}$ is activation packing and layout preparation, $T_{\text{D2H}}$ and $T_{\text{H2D}}$ are device-to-host and host-to-device transfers, $T_{\text{cpu}}$ is host-side computation of the missing LoRA contribution, and $T_{\text{merge}}$ is the cost of reintegrating the returned result into the device-side decode stream.

This decomposition makes explicit the asymmetry highlighted in Section~\ref{subsec:feasibility}. The synchronous payload on the cold path is activation- or residual-sized state, rather than the full expert--LoRA object. As a result, execution-first avoids placing full weight restoration on the current token's foreground path. Accordingly, $T_{\text{cold}}$ should be interpreted as the service time of the cold path, while the latency exposed to decode is only the non-overlapped portion of that service time.

\paragraph{Critical-path comparison with promotion-first.}
For comparison, a promotion-first recovery path incurs
\begin{equation}
T_{\text{promote}} = T_{\text{admit}} + T_{\text{H2D-weights}} + T_{\text{gpu}},
\end{equation}
where $T_{\text{admit}}$ captures admission and scheduling overhead for the restored object, $T_{\text{H2D-weights}}$ is the host-to-device transfer of weights, and $T_{\text{gpu}}$ is the subsequent GPU execution. In expert--LoRA serving, the dominant synchronous cost is often not the computation itself, but the need to move and admit a relatively large weight object before the faulting token can resume.

The key distinction is therefore not only total miss-recovery time, but where that time appears. Promotion-first treats miss handling as immediate residency restoration, so weight transfer and object admission remain prerequisites for progress on the faulting request. Execution-first instead shifts recovery onto a side path whose synchronous payload is smaller and whose exposed latency can be reduced whenever the GPU hot path still has other ready requests to execute.

In this sense, the comparison is fundamentally about decode-time cost structure rather than raw device preference. Promotion-first pays a weight-restoration cost before useful work on the miss can complete, whereas execution-first pays an activation-exchange plus host-execution cost whose visible impact depends on overlap. Realizing this advantage in practice, however, requires a cold path with bounded overheads and stable service time. We therefore next describe how CoLoRA realizes the CPU cold path as a practical substrate for decode-time miss handling.

\subsubsection{CPU Cold Path Realization}
\label{subsec:cpu-cold-path}

This component addresses Challenge~\ref{subsec:challenge-overlap} by turning execution-first recovery into a practical runtime path rather than a conceptual alternative. The CPU cold path is not intended to replace the GPU as the main execution engine. Its role is to provide a predictable, overlap-friendly substrate for unavoidable misses.

\paragraph{Activation packing.}
The first step is activation packing. Before issuing a cold-path transfer, CoLoRA reorganizes the relevant activations on the GPU into contiguous staging buffers. This coalescing reduces fragmentation in DMA traffic and amortizes fixed transfer overhead when multiple cold-path requests can be served together. Because decode activations are relatively small, careful packing matters not only for bandwidth utilization, but also for suppressing per-miss overhead.

\paragraph{Asynchronous staging.}
Transfers between device and host use pinned memory and are issued asynchronously on separate CUDA streams. This allows device-to-host activation movement and host-to-device result return to overlap opportunistically with foreground GPU work, subject to available copy-engine capacity and scheduler state. The design does not assume perfect overlap; rather, it preserves overlap whenever the hardware and workload permit it.

\paragraph{Host-side execution.}
On the host side, missing expert--LoRA computations are executed by vectorized CPU kernels. CoLoRA uses AVX-optimized implementations for the dense linear operations involved in LoRA execution, binds worker threads to dedicated cores to reduce scheduling jitter, and NUMA-aligns those workers with the GPU's PCIe root complex when applicable. These choices are intended to keep $T_{\text{cpu}}$ stable under repeated decode-time invocations. The design does not depend on claiming that CPU execution is generally faster than GPU execution. Instead, it depends on the more realistic claim that the cold path can be made efficient enough and predictable enough to overlap with useful GPU work in mixed hit/miss batches.

\paragraph{Result reintegration.}
Once host-side computation completes, the result is copied back to device memory and merged into the GPU-side execution state. This reintegration step is deliberately lightweight and avoids introducing a global barrier. Taken together, activation packing, asynchronous staging, vectorized CPU execution, and lightweight reintegration make the CPU a practical cold-path engine rather than a fallback of last resort.

With the cold path realized as a bounded execution substrate, the remaining challenge is to coordinate it with the GPU fast path without reintroducing implicit synchronization through scheduling. CoLoRA therefore requires a scheduler that preserves forward progress on GPU-resident work, dispatches cold-path jobs independently, and reinserts completed requests without forcing the execution stream back into lockstep.

\subsection{Decoupled Miss-Recovery Scheduler}
\label{subsec:scheduler}

The execution-first architecture relies on a runtime scheduler that explicitly decouples cold-miss handling from the main GPU execution stream. This scheduler bridges heterogeneous miss recovery with the dynamic admission model of continuous batching: rather than treating batch membership as fixed per decode step, it allows temporary, miss-induced evictions. The faulting request absorbs the cold-path cost, while unrelated ready requests continue making forward progress on the GPU.

\paragraph{Scheduler state model.}
Each request cycles through three states: \textit{GPU-Ready} (queued for hot-path execution), \textit{Cold-Path} (offloaded to the CPU after a miss), or \textit{Awaiting Reinsertion} (completed on the host, pending GPU-side merge). The scheduler maintains lock-free queues for each state and tracks a per-request layer counter to enforce strict intra-request ordering across decoupled execution phases. This phase-tracking mechanism allows cross-request divergence without breaking the decode pipeline.

\paragraph{Miss handling workflow.}
When a miss is detected at layer $L$, the scheduler atomically removes the request from the GPU-Ready queue, copies the required activations into a pinned staging buffer, and enqueues a cold-path job. The GPU dispatch loop continues issuing kernels for remaining ready requests without synchronization. Crucially, the skipped request's KV cache pointers and attention masks remain intact on the device; only the LoRA residual is deferred. Upon CPU completion, a host-side callback triggers an asynchronous D2H transfer of the computed residual. Once the transfer lands in device memory, the request is placed in the Awaiting Reinsertion queue. The scheduler's splice logic merges the residual into the GPU-side activation state at layer $L$ and returns the request to the GPU-Ready queue. Reinsertion uses per-layer CUDA events to guarantee that the merged state is visible before the request participates in subsequent attention computations, avoiding global barriers.

This organization yields decoupled miss recovery: GPU progress is no longer blocked by synchronous weight promotion. CoLoRA does not eliminate the per-request cost of handling a cold miss, but it transforms that cost from a large, batch-stalling PCIe migration into a bounded, CPU-side computation whose critical-path impact is minimized through asynchronous execution and overlap. Consequently, cold misses no longer inflate system-wide tail latency; their cost is isolated to the faulting request while the GPU continues serving ready work.

\paragraph{Bounded cold-path concurrency.}
To prevent the cold path from becoming a source of host-side queueing instability, CoLoRA caps the number of concurrent cold-path jobs to $K$ (tuned to host core count and PCIe copy-engine capacity). The scheduler enforces this bound via an atomic counter that blocks new cold-path submissions until a running job completes; excess misses are queued rather than dispatched. Within this bounded regime, the scheduler guarantees three invariants: (1) per-request layer ordering is strictly preserved, (2) cross-request execution phases may diverge, enabling overlap between cold-path computation and hot-path GPU work, and (3) GPU forward progress is maintained whenever the GPU-Ready queue is non-empty.

Decoupled scheduling addresses the current access but does not proactively improve future residency. To that end, CoLoRA layers locality-driven background optimizations (deferred promotion and temporal prefetching) that operate strictly off the critical path. These mechanisms improve hot-set concentration when beneficial but are never prerequisites for immediate forward progress.


\subsection{Locality-Driven Background Optimizations}
\label{subsec:locality-background}

Beyond execution-first miss recovery, CoLoRA incorporates locality-driven background optimizations that address Challenge~1 at the systems level. Once expert--LoRA objects are managed at fine granularity and working-set fragmentation becomes unavoidable, the system must improve future residency selectively rather than assume that a larger GPU hot set alone will absorb demand.

\paragraph{Deferred promotion.}
The first mechanism is deferred promotion. Although CoLoRA removes blocking promotion from the foreground miss-recovery path, promotion still matters for improving future GPU residency. The design change is therefore not to eliminate promotion, but to redefine its role. In CoLoRA, promotion no longer serves as the default recovery mechanism for the current miss. Instead, it is treated as a background optimization whose purpose is to increase the probability that subsequent accesses are served on the GPU hot path.

When a cold-path execution is triggered, CoLoRA may asynchronously enqueue the corresponding expert--LoRA object for promotion into GPU memory. This promotion is issued off the critical path and does not delay completion of the current token. In effect, cold-path execution handles the present access, while deferred promotion improves residency for future accesses when that investment is likely to pay off.

\paragraph{Reuse-aware admission.}
To prevent deferred promotion from degenerating into indiscriminate background traffic, CoLoRA uses a reuse-distance-aware admission policy. Let $\delta$ denote a reuse threshold. An object is admitted for asynchronous promotion only when it is expected to be reused within the next $\delta$ decode steps. Objects whose predicted reuse distance exceeds $\delta$ remain host-resident and continue to be served on demand through the cold path. This policy avoids spending PCIe bandwidth and GPU cache capacity on weakly reusable objects, and preserves the benefit of removing blocking promotion from the foreground path.

In the current design, $\delta$ is implemented as a static hyperparameter. A more adaptive policy that tunes $\delta$ online based on runtime signals such as observed reuse behavior, PCIe queue depth, or device-memory pressure is left to future work. Importantly, admission errors affect only future cache efficiency: they do not delay the current request and do not alter CoLoRA's execution-first semantics.

\paragraph{Temporal prefetching.}
The second mechanism exploits short-horizon temporal locality in decode to reduce the effective service time of future accesses. Our router traces show that consecutive decode tokens exhibit strong but layer-dependent routing continuity: the mean expert-set hit rate is 72.2\% overall, with early layers exceeding 95\%, middle layers dipping to 56.8\%, and late layers recovering to 87\% (Appendix~\ref{app:temporal-locality}, Figure~\ref{fig:temporal_locality_hit_rate}). Although long-horizon reuse of expert--LoRA objects can be weak under multi-tenant serving, this U-shaped per-layer pattern still indicates that near-future accesses are substantially more predictable than global cache behavior alone would suggest.

CoLoRA leverages this regularity using a lightweight temporal predictor that identifies expert candidates likely to be accessed in the next few decode steps and opportunistically prefetches the corresponding host-resident weights. The layer dependence of the trace signal suggests that this predictor should be viewed as an opportunistic background policy rather than an always-on dependency for forward progress. A request never waits for a prefetched object: if the required object is still unavailable when accessed, cold-path execution remains the default fallback. The purpose of prefetching is therefore not to guarantee stable residency in any specific CPU cache level, nor to assume that large expert weights remain fully resident in LLC. Rather, it improves effective access locality and can reduce the service time of subsequent cold-path invocations when the prediction is correct.

Because temporal prefetching is auxiliary to the main execution-first design, incorrect predictions consume only bounded background bandwidth and do not affect correctness or foreground progress. Taken together, deferred promotion and temporal prefetching preserve CoLoRA's guiding principle: the current access is served by whatever path can make immediate progress, while locality-driven mechanisms act only in the background to improve how similar accesses are handled later.


\section{Implementation}
\label{sec:implementation}

We implement CoLoRA by extending VaLoRA~\cite{mi2025empower}. We reuse VaLoRA's PagedAttention-based KV-cache manager, continuous batching scheduler, and token-based memory manager for the base model. Our modifications are confined to expert-layer LoRA execution and residency management.

CoLoRA replaces VaLoRA's adapter-centric caching granularity with an \emph{expert--LoRA joint-object} granularity, where each cache entry is keyed by a \((\textit{layer}, \textit{expert}, \textit{adapter})\) tuple. This matches the actual access granularity of multi-LoRA MoE decode. To preserve compatibility with VaLoRA's allocator, we reuse its slot-based cache accounting: an expert--LoRA joint object with LoRA rank \(r\) is charged \(r\) cache slots.

We add a residency-aware dispatch point to the inference loop and implement CoLoRA's cold path on the host, while keeping the base MoE expert computation on the GPU. On the host side, the LoRA residual runs on AVX kernels using a fixed worker pool pinned via \texttt{numactl}. We further use pinned staging buffers, asynchronous device--host transfers, and a bounded number of in-flight cold-path jobs to keep host-side execution stable under bursty misses.

We implement residency management as a background service, separate from foreground miss recovery. After cold-path execution, an object may be promoted asynchronously to GPU memory based on predicted reuse. Eviction reuses Chameleon~\cite{iliakopoulou2025chameleon}'s policy with static parameters \((F,R,S)=(0.45, 0.10, 0.45)\). We also implement a lightweight temporal prefetcher driven by recent routing history.

\section{Related Work}
\label{sec:related}

\paragraph{LoRA and multi-tenant adapter serving.}
LoRA introduced low-rank adaptation as a parameter-efficient way to specialize a shared foundation model with a small number of task-specific parameters \cite{hu2022lora}. Since then, a substantial body of work has studied efficient serving of many concurrent LoRA tenants, including heterogeneous batching, adapter paging, CPU-assisted loading, and SLO-aware scheduling \cite{chen2024punica,sheng2024slora,wu2024dlora,li2025toppings,bruel2024compress}. These systems form the closest prior art on the adaptation axis. However, they primarily target dense backbones, where the active adaptation state is naturally organized around adapters. In CoLoRA's setting, the base model is sparse and each decode step touches only the LoRA states associated with the routed experts for the current token. The relevant unit of access is therefore not an adapter alone, but an expert--LoRA joint object.

\paragraph{Sparse MoE models and serving.}
Sparse MoE architectures activate only a small subset of experts per token, making routing locality central to efficient inference \cite{shazeer2017outrageously,fedus2022switch,jiang2024mixtral,deepseek2024deepseekv2}. Correspondingly, recent MoE-serving systems study expert placement, offloading, caching, and CPU/GPU co-execution under memory pressure \cite{xue2024moe,kamahori2024fiddler,yu2025fmoe,zhong2025hybrimoe}. These works are directly relevant on the sparsity axis, but they reason primarily at expert granularity. CoLoRA addresses a different regime in which expert routing and tenant-specific adaptation interact, fragmenting reuse across a much larger space of expert--LoRA combinations. This difference is especially consequential during decode, where even infrequent cold accesses can surface directly on the per-token critical path and disproportionately affect tail latency.

\paragraph{LLM serving runtimes and hierarchical memory management.}
A complementary line of work studies the runtime substrate for efficient LLM inference, including iteration-level scheduling, continuous batching, KV-cache management, prefill/decode separation, and hierarchical use of host and device memory \cite{yu2022orca,kwon2023efficient,agrawal2023sarathi,patel2024splitwise,aminabadi2022deepspeed,sheng2023flexgen,na2025flexinfer}. CoLoRA builds on this systems context, but differs in how it handles cold weights on the decode path. Prior systems typically treat a miss as a promotion problem: weights are restored to accelerator memory before normal execution proceeds. CoLoRA instead targets cache-pressured multi-LoRA MoE decode, where many misses have weak near-term reuse and synchronous promotion can become a blocking synchronization point. In this sense, prior work has separately advanced adapter-centric LoRA serving, expert-centric MoE serving, and high-performance LLM runtime design, while CoLoRA combines these perspectives for a setting that none of them directly addresses: multi-tenant LoRA serving on sparse MoE backbones under decode-time cache pressure. Its central distinction is to make the expert--LoRA joint object the unit of control and to decouple miss recovery for the current token from residency restoration for future tokens.

\section{Per-Layer Temporal Routing Locality}
\label{app:temporal-locality}

Figure~\ref{fig:temporal_locality_hit_rate} reports the per-layer consecutive-token routing locality measured from the Qwen3--VL--MoE router on the ShareGPT--V3 trace. For each request and MoE layer, we compare the routed expert set at decode step $t$ against the previous decode step $t-1$ using the hit-rate metric $|E(L,t) \cap E(L,t-1)| / |E(L,t)|$. The resulting curve is distinctly U-shaped: early layers show very high temporal continuity, middle layers are weaker, and late layers recover. This observation motivates temporal prefetch as a useful but non-uniform optimization across depth.
