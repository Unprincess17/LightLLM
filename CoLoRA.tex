\begin{abstract}
Large-scale LLM serving is increasingly shaped by the convergence of sparse Mixture-of-Experts (MoE) base models and LoRA-based multi-tenant adaptation. In multi-LoRA MoE serving, tenant-specific LoRA modules are attached to sparsely activated expert layers, creating a regime where the effective unit of caching is a joint expert--LoRA object. Our trace-driven analysis shows this shift weakens hot-set concentration, reducing cache hit rates by up to 56\% compared to LoRA serving in dense models, and pushing performance degradation into the tail latency.

We present CoLoRA, a serving runtime that treats GPU memory misses as an execution-first recovery problem rather than a promotion-first caching problem. CoLoRA adopts a residency-aware hot/cold dual-path design: GPU-resident objects execute on the hot path, while GPU-cold objects trigger a CPU cold path that computes only the LoRA residual from host-resident weights and merges it back for the current token. CoLoRA further incorporates deferred promotion and temporal prefetching to improve future reuse and partially overlap cold-path latency. By decoupling cold-object execution from GPU residency management, CoLoRA prevents pipeline stalls during cache misses while preserving GPU compute saturation for hot tenants. Under high memory pressure, CoLoRA reduces P99 and P50 Time-Per-Output-Tokens (TPOT) latencies by XX\% and XX\%, respectively, over state-of-the-art baselines such as S-LoRA, while maintaining comparable throughput.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Large-scale LLM serving is increasingly shaped by the convergence of two trends: sparse Mixture-of-Experts (MoE) base models~\cite{todo:moe-llm} and LoRA-based multi-tenant adaptation~\cite{todo:lora-original,todo:lora-serving}. In practice, these trends meet in \emph{multi-LoRA MoE serving}. While existing multi-LoRA systems target dense modules such as attention layers and shared FFNs, they do not directly address adaptation on sparsely activated MoE expert layers~\cite{todo:lora-original,todo:lora-serving}. This gap is critical: MoE expert FFN blocks comprise the majority of model capacity, making them the natural target for tenant-specific specialization~\cite{todo:moe-knowledge-capacity, schulman2025lora}. This combination couples the compute efficiency of MoE with the parameter efficiency of LoRA. However, it creates a new serving regime in which request-time sparse routing and tenant-specific adapter selection jointly shape the active weights. This significantly enlarges and diversifies the inference working set, rendering it difficult to manage with existing caching strategies.

However, it also creates a distinct serving regime in which dynamic sparse routing~\cite{todo:moe-routing-dynamics} and long-tailed multi-tenant adaptation~\cite{todo:slora} jointly determine which expert- and adapter-side weights are needed for each request, increasing access diversity and complicating locality management during inference.

This enlarged and more diverse working set becomes especially problematic during \emph{decode} in prefill--decode deployments~\cite{todo:pd-serving}. Unlike prefill, which can often amortize weight-loading costs across many prompt tokens, decode operates under tight inter-token latency SLOs: generation is highly memory-bandwidth bound, and any weight miss on the critical path directly translates to pipeline stalls and ITL degradation. Consequently, the granularity of weight management becomes critical: in pure MoE serving, the natural unit is the expert; in conventional multi-LoRA serving, it is the adapter, and prior systems such as S-LoRA~\cite{todo:slora} and VaLoRA~\cite{mi2025empower} therefore adopt adapter-centric designs that assume dense adapter loading. In multi-LoRA MoE decode, however, a request only needs the LoRA residuals for the selected experts, so the effective unit of access and reuse is neither an expert alone nor an adapter alone, but a joint expert--LoRA object. These objects are substantially larger than the attention-side LoRA units emphasized in prior systems, because expert-layer LoRA scales with the FFN intermediate dimension (typically 4$\times$--8$\times$ the model width), whereas attention-side LoRA targets the narrower head projections~\cite{todo:moe-ffn-architecture}. At the same time, the base MoE model typically already occupies most device memory, leaving only limited residual VRAM for caching such objects~\cite{todo:large-moe-models}. This breaks the locality assumptions of prior caches: the enlarged and fragmented working set prevents concentration of hot expert--lora pairs, leading to cache thrashing and unpredictable decode latency.

To quantify the locality regime introduced by multi-LoRA MoE decode, we conduct a trace-driven study using Alibaba LoRA serving traces augmented with realistic MoE expert routing patterns~\cite{lin2025understanding}. The study shows that once access is modeled at the granularity of joint expert--LoRA objects, the hot set becomes markedly less concentrated. As shown in Figure~\ref{fig:motivation-breakdown}(a), access locality is highly concentrated under expert-only granularity: the top 2K cached objects cover 98.4\% of accesses. Under realistic joint-object modeling, however, this concentration collapses—the same top-2K set covers only 13.9\% and 21.8\% of accesses under independent (C1) and correlated (C2) adapter--expert assignment, respectively. This fragmentation makes simply adding cache capacity far less effective. In Figure~\ref{fig:motivation-breakdown}(b), the expert-only oracle reaches its target P99 TPOT with a cache that stores just 2K objects, whereas the realistic joint-object workloads still fail to reach that same target even when the cache is expanded to 65K objects (over 32$\times$ larger). Together, these results show that in multi-LoRA MoE decode, capacity misses are not transient anomalies that can be eliminated by modest cache growth; they are persistent tail events on the decode critical path.

Once GPU capacity misses become unavoidable, the central problem shifts from \emph{how to avoid misses} to \emph{how to serve them on the decode critical path}. Existing GPU-centric systems typically handle a miss with a load-then-run policy: the required weights are first promoted from host memory to GPU memory, and execution resumes only after that promotion completes~\cite{todo:gpu-offload}. This approach is effective when misses are infrequent and future reuse is sufficient to amortize migration cost. In multi-LoRA MoE decode, however, a capacity miss often incurs PCIe transfer latency that dwarfs the lightweight LoRA kernel executing for a single token, leaving minimal compute work to amortize transfer latency or guarantee near-term reuse. In this regime, promotion-first recovery fails not merely due to PCIe bandwidth limits, but because weight transfer becomes a \emph{blocking synchronization point} that directly stalls the token generation pipeline. The resulting systems question is therefore: when a joint expert--LoRA object is GPU-cold, should the current token stall for synchronous promotion, or should the miss take a different execution path?

We address this problem with CoLoRA, a decode-time runtime for multi-LoRA MoE serving that replaces blocking promotion-first recovery with execution-first heterogeneous miss recovery. CoLoRA uses a residency-aware hot/cold dual-path design for expert--LoRA computation during decode. Cache-resident adapters remain on the GPU hot path, while GPU-cold adapters are handled through a separate cold path rather than triggering immediate synchronous promotion. Crucially, CoLoRA does not offload the full expert computation to the CPU, nor does it assume host execution is generally faster than GPU execution. Instead, it exploits a decode-time data-movement asymmetry: computing a cold LoRA residual on the CPU exchanges only per-token activation vectors, whereas promotion-first recovery must first transfer the full expert--LoRA weight object to the GPU. The base MoE expert computation therefore remains on the GPU, while the corresponding cold LoRA residual is computed on the CPU from host-resident weights and merged back for the current token. By detaching only the cold LoRA contribution from blocking promotion, CoLoRA treats GPU-cold misses as bounded heterogeneous execution events rather than unconditional migration barriers on the decode critical path.

\section{Background, Motivation, and Challenges}
\label{sec:background}

\subsection{Background: Expert--LoRA Computation in Multi-LoRA MoE Decode}
\label{subsec:background}

In decode-time serving of large language models, combining a shared sparse Mixture-of-Experts (MoE) base model with multiple LoRA specializations introduces a complex, fine-grained parameter access pattern. During decode, each generated token triggers dynamic routing within the base model, while concurrent requests invoke different, task-specific LoRA adapters. Consequently, the serving system must repeatedly resolve both the activated experts and the adapter-specific LoRA states on the latency-critical decode path.

This interaction changes the natural unit at which the system should reason about locality and misses. In dense multi-LoRA serving, accesses often concentrate on a single adapter's weights, making adapter-level reasoning sufficient in many cases. In MoE decode, however, each token activates only a small routed subset of experts, and LoRA computation is needed only for the routed experts of the current request. The relevant access unit is therefore not an expert or an adapter in isolation, but their joint occurrence in the decode path, which we refer to as an \emph{expert--LoRA joint object}.

This distinction matters particularly in decode. Decode operates at small effective batch sizes, repeats routing and parameter-access decisions once per token, and exposes miss-handling overheads directly on the latency-critical path. Consequently, when expert--LoRA joint objects do not fit cleanly within practical GPU cache budgets, the key systems question is not only how to manage residency, but also how to recover cold misses without inflating per-token latency.


\subsection{Motivation: Joint-Object Modeling Fragments Decode Locality}
\label{subsec:motivation}

\subsubsection{Expert--LoRA Joint Objects as the Relevant Access Unit}
\label{subsec:joint-object}

A central question is what abstraction the system should use to reason about locality, residency, and misses.

In sparse MoE decode, each token activates only a small subset of routed experts. Once multiple LoRA adapters coexist, accesses no longer concentrate on entire adapters or on experts alone, but on LoRA states attached to specific routed experts. This makes expert--LoRA joint objects the relevant access unit for decode-time serving.

Reasoning at coarser granularity obscures the true access pattern. Adapter-level management is too coarse because it retains many expert slices together with the few that are actually needed for the current token. Expert-level management is incomplete in multi-tenant serving because it ignores adapter identity: while the expert set is fixed, LoRA adapters vary across requests, so collapsing accesses by expert alone systematically overestimates reuse across tenants. To understand the consequences of this change in access granularity, we next compare decode locality and system behavior under expert-only and expert--LoRA joint-object conditions.


\subsubsection{Joint Objects Fragment Decode Locality}
\label{subsec:case-study}

To examine whether this finer-grained access view matters in practice, we conduct a trace-driven case study under three workload conditions.
\texttt{C0} uses expert-only keys.
\texttt{C1} uses expert--LoRA joint keys under independent assignment, where adapter identity is sampled independently of expert routing.
\texttt{C2} uses the same expert--LoRA joint keys under correlated assignment, where certain adapters are more likely to co-occur with specific experts.
This setup separates the effect of finer-grained keying itself from the extent to which structured adapter--expert affinity can partially preserve locality.
We use Alibaba trace~\cite{lin2025understanding} to model LoRA serving request arrivals and LoRA invocations, and replay the resulting decode access streams under these conditions.

As illustrated in Figure \ref{fig:motivation-breakdown}, modeling accesses as joint objects triggers a cascade of system-level degradations, demonstrating that traditional caching strategies are insufficient for this workload.

\paragraph{Locality breaks under joint objects.}
Moving from coarse-grained to joint-object modeling severely fragments decode locality. Figure \ref{fig:motivation-breakdown}(a) shows that the access distribution flattens substantially when expert routing and adapter identity are modeled jointly. Because the access frequency is distributed across a combinatorial space of expert--lora pairs, the "hot set" shrinks in dominance. Consequently, a bounded GPU cache captures a significantly smaller fraction of total accesses, leading to longer reuse distances and frequent cold starts.

\paragraph{Cache scaling loses effectiveness.}
Because locality is fundamentally weakened, simply increasing GPU cache capacity does not resolve the problem. Figure~\ref{fig:motivation-breakdown}(b) shows that, although the expert-only layout reaches its target P99 TPOT with only 2K cached objects, the joint-object layouts remain substantially above the same target across the entire cache sweep and still fail to recover it even at 65K cached objects. This means the issue is not merely insufficient cache capacity: once object granularity destroys locality, scaling cache size yields limited benefit. In practice, systems must therefore operate under constrained budgets where cold misses remain unavoidable.

\paragraph{Tail latency explodes under misses.}
The most severe consequence of this locality fragmentation manifests in request latency. Figure \ref{fig:motivation-breakdown}(c) evaluates Time Per Output Token (TPOT) under a practical GPU cache budget. While the median TPOT remains near-optimal at approximately 1.2 ms, the degradation is heavily concentrated in the tail. P99 latency increases by roughly 5.6x. Because decode operations repeat routing and parameter-access decisions token by token, cold misses stall the synchronous execution path, disproportionately penalizing tail requests that happen to traverse un-cached expert--LoRA intersections.

Taken together, these results show that the key problem in multi-LoRA MoE decode is no longer only cache efficiency in the traditional sense. Once expert--LoRA joint objects become the effective unit of access, the remaining performance loss is increasingly determined by how unavoidable cold misses are handled on the decode critical path.

\subsubsection{Why execution-first is feasible on decode}
\label{subsec:feasibility}
The results above show that, once expert--LoRA joint objects become the effective unit of access, cold misses remain persistent under practical GPU cache budgets. At that point, the central systems question is no longer only how to enlarge the hot set, but how to serve a miss on the latency-critical decode path. In decode, this question is particularly important because execution proceeds token by token, batching opportunities are limited, and any synchronous miss-handling step is exposed directly in per-token latency.

\begin{figure}[t]
  \centering
  \includegraphics[width=\linewidth]{figures/miss_cost_compare.pdf}
  \caption{
    \textbf{Promotion-first vs. execution-first synchronous miss cost.}
    Promotion-first recovery restores the full expert--LoRA object before execution can resume, making weight migration part of the current token's foreground miss cost.
    Execution-first recovery instead exchanges activation/residual-sized state, computes only the missing LoRA contribution on the CPU, and merges the result back into the decode stream.
    The key distinction is therefore what data must be moved synchronously on the decode critical path, rather than a claim that CPU execution is universally faster.
  }
  \label{fig:miss-cost-compare}
\end{figure}

A key observation is that a decode-time cold miss introduces an asymmetry between restoring residency and serving the current token, as shown in figure~\ref{fig:miss-cost-compare}. 
Under a conventional promotion-first policy, the system must first move the missing expert--LoRA object into GPU memory and only then resume execution. However, for the current token, what is immediately needed is not full residency restoration as a goal in itself, but completion of the missing expert--LoRA contribution for the routed expert. This distinction matters because expert-layer LoRA objects are relatively large, whereas the per-token activation state involved in the current decode step is comparatively small. As a result, the synchronous cost of promotion-first recovery is dominated by moving a large weight object onto the device before useful work can continue.

This asymmetry suggests that feasibility should be judged not by asking whether CPU execution is universally faster than GPU execution, but by asking what portion of miss-recovery latency must appear on the current token's critical path. If the system can complete the missing LoRA contribution by exchanging activation-sized state while leaving the base expert computation on the GPU, then a cold miss no longer has to be treated as an unconditional residency-restoration barrier. Instead, it can be handled as a bounded execution event whose visible cost depends on how much of that work can be overlapped with other ready GPU computation.

This perspective is especially relevant in multi-tenant MoE decode, where mixed hit/miss batches are common and misses are not perfectly synchronized across requests. In such settings, forcing every cold object through immediate promotion risks turning a per-request miss into a group-wide stall. By contrast, an execution-first design has the potential to isolate the miss to the faulting request while allowing other ready requests to continue making progress on the GPU. The goal, therefore, is not to replace GPU execution for the common case, but to provide a miss-recovery path whose exposed latency is better matched to the decode-time cost structure of joint expert--LoRA accesses.

This argument does not imply that execution-first recovery is always preferable. When adapter diversity is low, the effective working set fits comfortably in GPU memory, or near-term reuse is strong enough to amortize immediate promotion, a load-then-run policy becomes more competitive. CoLoRA therefore targets the regime identified by Figure~\cite{TODO}: cache-pressured multi-LoRA MoE decode, where joint-object locality is structurally fragmented, cold misses remain unavoidable, and miss recovery should be optimized for exposed latency rather than immediate residency restoration.


\subsection{Challenges}
\label{subsec:challenges}

The empirical results above reveal a fundamental shift in the role of caching for multi-LoRA MoE decode serving. Once expert--LoRA joint objects become the effective unit of access, locality degradation makes cold misses difficult to eliminate within practical GPU cache capacity alone. Cold misses are therefore no longer rare anomalies that can be absorbed by a sufficiently large hot set. Instead, they become persistent events on the latency-critical decode path, and the dominant systems question shifts from how to avoid every miss to how to recover unavoidable misses without inflating per-token latency.

Realizing this shift in a practical serving runtime requires addressing three challenges.

\paragraph{Challenge 1: Reasoning at expert--LoRA granularity under expanded and fragmented working sets.}
\label{subsec:challenge-residency}

Under joint-object modeling, the effective key space expands substantially, while reuse becomes weaker and more fragmented across requests. This makes coarse-grained management ineffective: adapter-level residency retains many expert slices that are never touched, whereas expert-only reasoning overestimates reuse by ignoring adapter diversity. At the same time, naive fine-grained residency increases fragmentation pressure on the effective hot set and makes limited GPU capacity more vulnerable to transient cold objects.

The system must therefore reason at expert--LoRA granularity, which matches actual computation, without assuming that caching alone can absorb the resulting working-set expansion.

\paragraph{Challenge 2: Recovering cold misses without forcing promotion-first stalls on decode.}
\label{subsec:challenge-miss}

In this regime, many misses correspond to cold objects whose near-term reuse is too limited to amortize immediate promotion. If the system continues to apply a conventional load-then-run policy, each such miss becomes a blocking recovery event: the current token must wait for weight migration before expert--LoRA computation can proceed. Under decode-time latency sensitivity, this directly amplifies tail latency.

The system therefore needs a different default recovery strategy for cold misses. Instead of forcing all misses through immediate GPU promotion, it must provide a way to complete the current expert--LoRA computation without making promotion the only recovery path, while still preserving the option to promote objects later when future reuse justifies it.

\paragraph{Challenge 3: Making cold-path recovery practical under decode constraints.}
\label{subsec:challenge-overlap}

Changing the miss-recovery abstraction is not sufficient by itself. If cold-path execution is too slow, the system merely replaces GPU promotion stall with CPU-side stall. If it is poorly integrated with the decode pipeline, heterogeneous execution introduces a new source of queueing and tail behavior rather than alleviating the original one.

The system must therefore make cold-path recovery efficient enough to operate at small, irregular decode batch sizes, and organize execution to preserve opportunities for overlap between cold-miss handling and GPU hot-path or base-model computation whenever dependencies allow. The challenge is not only to provide an alternative recovery path, but to ensure that this path reduces exposed miss latency instead of becoming a new bottleneck.

\section{Design}
\label{sec:design}

\subsection{Hot/Cold Execution-First Architecture}
\label{subsec:dual-path-handling}

\begin{figure}[h]
  \centering
  \includegraphics[width=\linewidth]{figures/architecture.pdf}
    \caption{\textbf{CoLoRA's execution-first hot/cold dual-path architecture for decode-time expert--LoRA serving.} Routed expert--LoRA accesses check GPU residency; hits remain on the GPU hot path, while miss requests peel off to a CPU cold path that computes only the LoRA residual and later reinserts the result. Deferred promotion is decoupled from foreground miss recovery and serves future reuse only.}
  \label{fig:CoLoRA_overview}
\end{figure}

CoLoRA is motivated by a simple observation: under multi-tenant expert--LoRA serving, cold misses cannot be treated as rare exceptions. Once the unit of management becomes the expert--LoRA joint object, the effective working set expands and fragments, and misses remain common under realistic GPU memory budgets. In decode, where execution proceeds token by token and batching opportunities are limited, each such miss can directly surface as a stall on the current token's critical path.

The design objective is therefore not to eliminate every miss, but to prevent a cold miss from becoming a global synchronization event. CoLoRA does so by changing the default recovery action. Instead of synchronously restoring missing weights to the GPU and only then resuming execution, it adopts an execution-first policy: the system prioritizes completing the missing expert--LoRA computation using immediately available resources, while treating weight promotion as a separate optimization for future reuse.

More broadly, CoLoRA is built around a uniform design philosophy: the mechanism that guarantees progress for the current token should be separated from the mechanisms that improve locality for future tokens. This separation allows miss handling to remain latency-oriented and correctness-critical, while promotion and prefetching remain opportunistic optimizations rather than mandatory recovery steps.

This leads to a hot/cold dual-path design for expert--LoRA computation in decode. When the required expert--LoRA object is resident, execution proceeds on the GPU hot path with no change to the normal fast path. When the object is absent, the request is diverted to a CPU cold path that completes the current LoRA computation using host-resident parameters. The key point is that the miss no longer forces the entire execution group to wait for immediate promotion.

The runtime realizes this behavior through a skip-and-reinsert discipline. If request $i$ encounters a miss at layer $L$, it is temporarily removed from the current GPU execution group, and its activation state is staged for host-side execution. The GPU then continues processing other ready requests at the same layer without waiting. Once the CPU cold path finishes the missing expert--LoRA computation, the result is returned to the device and request $i$ resumes from the next execution point. In effect, a cold miss delays only the affected request, rather than serializing all requests that happened to be grouped with it.

This design preserves three invariants that are central to correctness. First, each request still advances strictly in layer order. Second, different requests are allowed to be temporarily out of phase, which creates room for overlap rather than forcing lockstep execution. Third, a miss in one request does not block the progress of other ready requests. Together, these invariants allow CoLoRA to convert unavoidable misses from global stalls into localized delay.

The design is particularly well matched to decode-time serving, where per-adapter batch sizes are small, routing decisions are heterogeneous across requests, and misses are not perfectly synchronized. In this regime, even modest overlap between hot-path GPU execution and cold-path CPU execution can substantially reduce the visible impact of cold misses. The next subsection therefore examines the cost structure of this execution-first recovery path and clarifies why its critical-path placement is more favorable than promotion-first recovery.

\subsubsection{Cost Structure of Cold-Path Execution}
\label{subsec:analytical-formulation}

Execution-first miss handling replaces synchronous weight promotion with a sequence that moves activations to the host, computes the missing LoRA contribution there, and returns the result to the device. The latency of a cold-path invocation can be decomposed as
\begin{equation}
T_{\text{cold}} = T_{\text{pack}} + T_{\text{D2H}} + T_{\text{cpu}} + T_{\text{H2D}} + T_{\text{merge}},
\end{equation}
where $T_{\text{pack}}$ denotes activation packing and layout preparation, $T_{\text{D2H}}$ and $T_{\text{H2D}}$ are device-to-host and host-to-device transfers, $T_{\text{cpu}}$ is host-side computation, and $T_{\text{merge}}$ is the cost of reintegrating the result into the device-side execution stream.

This decomposition matters because, in decode, the transferred activation payload is typically much smaller than the missing expert--LoRA weights themselves. As a result, execution-first avoids placing full weight movement on the current token's critical path. The dominant concern is therefore not whether the CPU path is universally faster in absolute time, but whether enough of its latency can be overlapped with ongoing GPU work on other requests.

For comparison, a promotion-first recovery path incurs
\begin{equation}
T_{\text{promote}} = T_{\text{admit}} + T_{\text{H2D-weights}} + T_{\text{gpu}},
\end{equation}
where $T_{\text{admit}}$ captures admission and scheduling overheads for the restored object, $T_{\text{H2D-weights}}$ is the host-to-device transfer of weights, and $T_{\text{gpu}}$ is the subsequent GPU execution. In expert--LoRA serving, the transfer and preparation of weights are often the dominant terms. More importantly, promotion-first keeps those costs on the synchronous recovery path of the current token.

The central distinction, then, is not merely one of total latency but of critical-path placement. Promotion-first makes recovery latency visible immediately because execution must wait for residency restoration. Execution-first instead turns recovery into a parallel side path whose visible cost is reduced whenever the hot path still has useful work to perform. This observation directly informs the runtime design: CoLoRA must minimize fixed per-miss overheads, keep cold-path execution bounded and predictable, and preserve overlap whenever ready GPU work remains. We next describe the scheduler that realizes this decoupling in the runtime.

\subsubsection{CPU Cold Path Realization}
\label{subsec:cpu-cold-path}

The CPU cold path is designed not as a throughput replacement for the GPU, but as a predictable execution engine for unavoidable misses. Its job is to make execution-first recovery viable in decode by keeping miss handling bounded, overlap-friendly, and implementation-efficient.

The first step is activation packing. Before a cold-path transfer is issued, the relevant activations are reorganized on the GPU into contiguous staging buffers. This activation coalescing reduces fragmentation in DMA traffic and amortizes transfer overheads when multiple cold-path requests can be handled together. Because decode activations are relatively small, careful packing matters not only for bandwidth efficiency, but also for reducing fixed per-miss overheads.

Transfers between device and host use pinned memory and are issued asynchronously on separate CUDA streams. This allows device-to-host activation movement and host-to-device result return to overlap opportunistically with foreground GPU work, subject to available copy-engine capacity and scheduler state. The goal is not to assume perfect overlap, but to preserve it whenever the hardware and workload permit.

On the host side, missing expert--LoRA computations are executed by vectorized CPU kernels. CoLoRA uses AVX optimized implementations for the dense linear operations involved in LoRA execution, binds worker threads to dedicated cores to reduce scheduling jitter, and NUMA-aligns those workers with the GPU's PCIe root complex when applicable. These choices are intended to keep $T_{\text{cpu}}$ stable and predictable under repeated decode-time invocations. The system does not rely on the claim that CPU execution is generally faster than GPU execution. Instead, it relies on the more realistic and more important claim that the cold path can be made sufficiently efficient and sufficiently stable to overlap with useful GPU work in mixed hit/miss batches.

Once the host computation completes, the result is copied back and merged into the device-side execution state. This reintegration step is deliberately lightweight and avoids introducing a global barrier. In combination, activation coalescing, asynchronous staging, and vectorized host execution turn the CPU into a practical cold-path engine rather than a fallback of last resort.

With this execution substrate in place, CoLoRA can cleanly separate the mechanism that serves a miss now from the mechanisms that improve how likely similar accesses are to be served more efficiently later. We therefore turn to the locality-driven optimizations layered on top of the execution-first core.


\subsection{Decoupled Miss-Recovery Scheduler}
\label{subsec:scheduler}

The execution-first design depends on a runtime scheduler that explicitly decouples cold-miss handling from the main GPU execution stream. Conceptually, each request alternates among three states: it is either ready to execute on the GPU hot path, being processed on the CPU cold path after a miss, or waiting to be reinserted once a cold-path result has returned. The scheduler maintains corresponding queues for GPU-ready work, CPU cold-path jobs, and completed results awaiting reintegration.

When a miss occurs at layer $L$, the scheduler removes the affected request from the GPU-ready set, materializes its activations into a staging buffer, and submits a cold-path job to the CPU side. Crucially, the GPU does not wait for this job to complete. It immediately continues issuing kernels for the remaining ready requests. When the cold-path job finishes, the result is transferred back to device memory and the request is reintroduced into GPU execution at the appropriate continuation point.

This organization gives the system \emph{decoupled miss recovery}: GPU progress is no longer tied to immediate weight promotion for every cold object. More precisely, the request that incurs the miss still waits for its own cold-path result before it can advance, but other ready requests do not need to synchronize on that recovery. CoLoRA therefore does not eliminate cold-miss latency; instead, it isolates that latency to the faulting request and prevents a single miss from turning into a group-wide stall.

To keep the cold path from turning into an uncontrolled source of backlog, CoLoRA uses an explicit bound on cold-path concurrency. Only a limited number of cold jobs may be in flight at once, and excess misses are queued rather than launched immediately. This keeps host-side resource usage predictable and avoids replacing one form of global instability with another. Within this bounded regime, the scheduler preserves per-request layer ordering, allows cross-request phase decoupling, and maintains forward progress on the GPU whenever ready work exists.

This scheduler is the runtime embodiment of CoLoRA's core philosophy: demand execution is serviced immediately through the hot path or the cold path, while all other optimizations remain secondary to forward progress. Realizing that philosophy in practice, however, requires a cold path whose overheads are low and predictable enough to overlap with useful GPU work.


\subsection{Locality-Driven Background Optimizations}
\label{subsec:locality-background}

Beyond execution-first miss recovery, CoLoRA incorporates two locality-driven background optimizations that improve future access efficiency without reintroducing promotion-first behavior on the current token's critical path.

The first is deferred promotion. While CoLoRA removes blocking promotion from the foreground miss-recovery path, promotion remains important for improving future GPU residency. The key design change is therefore not to eliminate promotion, but to redefine its role. In CoLoRA, promotion no longer serves as the default recovery mechanism for the current miss. Instead, it is treated as a background optimization whose purpose is to increase the likelihood that subsequent accesses are served on the GPU hot path.

When a cold-path execution is triggered, CoLoRA may asynchronously enqueue the corresponding expert--LoRA object for promotion into GPU memory. This promotion is issued off the critical path and does not delay completion of the current token. In effect, cold-path execution handles the present access, while deferred promotion improves cache residency for future accesses if the object is likely to be reused.

To prevent promotion from degenerating into indiscriminate background traffic, CoLoRA employs a reuse-distance-aware admission policy. Let $\delta$ denote a reuse threshold. An object is admitted for asynchronous promotion only when it is expected to be reused within the next $\delta$ decode steps. Objects whose predicted reuse distance exceeds $\delta$ remain host-resident and continue to be served on demand through the cold path. This policy avoids wasting PCIe bandwidth and GPU cache capacity on weakly reusable objects, and preserves the benefit of removing blocking promotion from the foreground execution path.

In the current design, $\delta$ is implemented as a static hyperparameter. A more adaptive policy that tunes $\delta$ online based on runtime signals, such as observed reuse behavior, PCIe queue depth, or device-memory pressure, is left to future work. Importantly, admission errors affect only future cache efficiency: they do not delay the current request and do not alter CoLoRA's execution-first miss-handling semantics.

The second optimization exploits short-horizon temporal locality in decode to reduce effective cold-path service time. Our router traces show that consecutive decode tokens exhibit strong but layer-dependent routing continuity: the mean expert-set hit rate is 72.2\% overall, with early layers exceeding 95\%, middle layers dipping to 56.8\%, and late layers recovering to 87\% (Appendix~\ref{app:temporal-locality}, Figure~\ref{fig:temporal_locality_hit_rate}). Although long-horizon reuse of expert--LoRA objects can be weak under multi-tenant serving, this U-shaped per-layer profile still indicates that near-future accesses are substantially more predictable than global cache behavior might suggest.

CoLoRA leverages this regularity using a lightweight temporal predictor that identifies expert candidates likely to be accessed in the next few decode steps and opportunistically prefetches the corresponding host-resident weights. The layer dependence of the trace signal suggests that this predictor should be viewed as an opportunistic background policy rather than an always-on dependency for forward progress. Importantly, prefetching does not participate in demand execution: a request never waits for a prefetched object, and cold-path execution remains the default fallback when the required object is not yet available. The purpose of this mechanism is therefore not to guarantee stable residency in any particular CPU cache level, nor to assume that large expert weights remain fully resident in LLC. Rather, it improves effective access locality and reduces the service time of subsequent cold-path invocations when the prediction is correct.

Because temporal prefetching is auxiliary to the main execution first design, incorrect predictions consume only the bounded background bandwidth and do not affect correctness or foreground progress. Taken together, deferred promotion and temporal prefetching preserve CoLoRA's uniform design philosophy: misses are served immediately through execution first recovery, while locality-driven background mechanisms optimize how similar accesses are handled later.


\section{Implementation}
\label{sec:implementation}

We implement CoLoRA by extending VaLoRA~\cite{mi2025empower}. We reuse VaLoRA's PagedAttention-based KV-cache manager, continuous batching scheduler, and token-based memory manager for the base model. Our modifications are confined to expert-layer LoRA execution and residency management.

CoLoRA replaces VaLoRA's adapter-centric caching granularity with an \emph{expert--LoRA joint-object} granularity, where each cache entry is keyed by a \((\textit{layer}, \textit{expert}, \textit{adapter})\) tuple. This matches the actual access granularity of multi-LoRA MoE decode. To preserve compatibility with VaLoRA's allocator, we reuse its slot-based cache accounting: an expert--LoRA joint object with LoRA rank \(r\) is charged \(r\) cache slots.

We add a residency-aware dispatch point to the inference loop and implement CoLoRA's cold path on the host, while keeping the base MoE expert computation on the GPU. On the host side, the LoRA residual runs on AVX kernels using a fixed worker pool pinned via \texttt{numactl}. We further use pinned staging buffers, asynchronous device--host transfers, and a bounded number of in-flight cold-path jobs to keep host-side execution stable under bursty misses.

We implement residency management as a background service, separate from foreground miss recovery. After cold-path execution, an object may be promoted asynchronously to GPU memory based on predicted reuse. Eviction reuses Chameleon~\cite{iliakopoulou2025chameleon}'s policy with static parameters \((F,R,S)=(0.45, 0.10, 0.45)\). We also implement a lightweight temporal prefetcher driven by recent routing history.
