Slide 1

CoLoRA: Network-Aware LoRA Miss Recovery for Distributed MoE Serving

Gong Shufan

Problem

MoE serving already spends network budget on expert-parallel traffic. LoRA cache misses add recovery work exactly when decode latency is most visible.

Insight

Miss recovery is not a fixed CPU-vs-GPU choice. The best path depends on decode batch size, adapter rank, cache reuse, and live fabric pressure.

Contribution

CoLoRA combines local CPU/GPU crossover evidence, cross-machine recovery strategies, and network-aware scheduling for miss recovery in distributed MoE + LoRA serving.

Slide 2

The Miss Problem in MoE + LoRA Serving

Serving many LoRA adapters over MoE creates a second locality problem beyond expert placement.

Setup

  • Requests carry adapter IDs; hot adapters may be cached locally.
  • Decode executes repeatedly at small batch sizes, where every miss can affect TPOT.
  • MoE routing simultaneously consumes cross-GPU or cross-node bandwidth.

Why misses are common

  • Long-tail adapters exceed per-GPU cache capacity.
  • Load balancing and expert placement move requests away from cached adapters.
  • Multi-tenant arrivals change the hot set over time.
Current approach: fetch or recompute the missing LoRA weights on the critical path, usually without asking whether the network is already under EP pressure.

The Cross-Machine Challenge

A miss on UM253 may be recoverable from UM251, but the same fabric is also carrying expert-parallel traffic.

UM253 request stream
  ├─ local adapter cache: miss
  ├─ local CPU recovery: possible
  └─ remote path to UM251: adapter / delta / promotion

UM251 adapter state
  ├─ cached LoRA weights
  ├─ candidate for reuse-aware promotion
  └─ shares network with MoE EP all-to-all

Slide 7b

Insight: EP Load ≠ Effective Contention

Nominal load settings are not enough; CoLoRA needs path-specific fabric pressure signals.

Why nominal load can fail

  • Traffic may use a different path or queue pair than miss recovery.
  • Timing may not overlap the recovery transfer window.
  • Host, socket, and IPoIB effects can hide or reshape fabric contention.

Pressure signals to prefer

  • Per-path latency of recent recovery operations.
  • IB counters aligned with the target link and time window.
  • Queueing delay or retry signals from the actual communication path.
Schedule against measured, path-specific, time-local fabric pressure—not against nominal EP load labels.
Slide 8

CoLoRA Design: Hybrid Recovery Policy

Recover the current token quickly, then decide whether promotion is worth the network cost.

On LoRA cache miss during decode
  ├─ estimate local crossover: rank, N_dec, CPU/GPU cost
  ├─ estimate reuse: adapter popularity, active sequences, remaining tokens
  ├─ sense fabric pressure: recent path latency + counters
  └─ choose
      ├─ CPU foreground recovery
      ├─ GPU recovery when batch/rank crosses over
      └─ deferred remote promotion when reuse is high and pressure is low
  • Foreground path optimizes the current decode step.
  • Promotion path optimizes future reuse, not immediate correctness.
  • The policy can be conservative: CPU-first for small N_dec, promote only when predicted reuse pays back.
Slide 9

CoLoRA Design: Network-Aware Scheduling

Scheduling integrates EP pressure and adapter pre-cache opportunities before choosing a recovery path.

Request arrives with adapter A
  ├─ EP scheduler predicts expert traffic window
  ├─ adapter cache manager checks local and remote A
  ├─ pressure monitor reports path-specific fabric state
  └─ CoLoRA scheduler
      ├─ sense pressure
      ├─ pre-cache or defer promotion when safe
      └─ pick CPU / GPU / remote path for this miss
  1. Sense: use recent recovery latency and IB counters for the target path.
  2. Pre-cache: move adapters ahead of demand only when reuse is likely and EP pressure is low.
  3. Pick path: choose CPU, GPU, or remote recovery based on crossover and live pressure.
CoLoRA turns LoRA miss recovery from a fixed transfer decision into a network-aware scheduling decision.

Slide 11

Key Takeaways

  1. LoRA miss recovery is the bottleneck in MoE + LoRA serving at practical cache budgets.
  2. Local decode miss recovery is CPU-first at typical decode batches, especially N_dec ≤ 8.
  3. Cross-machine recovery requires pre-caching; S3 is 1.5–7× faster than naive weight transfer.
  4. EP load is a poor proxy for contention; CoLoRA should schedule on measured fabric pressure.
  5. CoLoRA adapts to the regime: local CPU-first, local GPU for large batches, cross-machine pre-cache plus relay, and pressure-aware scheduling.
